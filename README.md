# Quiet Ops

Quiet Ops is a lightweight, single-node hosting control panel for static sites, WordPress on Nginx/OpenLiteSpeed, Next.js, and Node.js.

See [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md) for the delivered phases, host rollout, resource profile, and verification checklist.

The current implementation is a runnable control plane with dry-run and live-host seams:

- Node 26 control plane using the built-in SQLite driver.
- React/Vite operator console with a responsive Quiet Ops visual system.
- Typed site lifecycle, deployments, manual encrypted backup manifests with database dump restore for MariaDB/PostgreSQL, stack switching, audit history, jobs, resource posture, local metric history, and webhook registration.
- Demand-started MariaDB/PostgreSQL/Redis provisioning recipes behind the host agent; live credentials are generated by the agent and written to a site-confined `secrets/*.env` file, never returned by MCP.
- The Ubuntu bootstrap installs database packages without starting all three daemons; the host agent starts only the requested engine, preserving the 1 GiB micro profile as far as the workload allows.
- Manual backups can upload the already-encrypted bundle to an operator-supplied public HTTPS presigned URL; the panel does not store cloud credentials or schedule server backups.
- MariaDB and PostgreSQL dumps are replayed during restore; Redis uses a namespace-scoped per-key serialized export/import because the supported Redis layout is shared.
- The micro-profile backup guard caps a bundle at 4,096 files / 256 MiB; larger sites should use a dedicated backup worker rather than starving the 1 GiB node.
- Public SSH keys can be installed per site; the agent writes forced-command, SFTP-only `authorized_keys` entries and never accepts private key material.
- Private MCP JSON-RPC endpoint with read resources, typed tools, approval previews, and a secretless site-workspace contract.
- Go `panel-agentd` source implementing the narrow Unix-socket host seam in safe dry-run mode.
- The agent service itself is capped at 512 MiB, one CPU, and 512 tasks so site-confined workspace/build jobs cannot consume the whole micro node.
- Per-site PHP-FPM pools for the Nginx WordPress path, with ondemand workers, site identities, socket permissions, and an `open_basedir` boundary.
- The Nginx and OpenLiteSpeed workers receive read-only ACLs on published releases; they never join the writable `quiet-ops` group. The privileged agent socket uses a separate `quiet-ops-control` group that only the panel account joins, so web workers cannot invoke root operations.
- Panel and agent environment files are also owned by `quiet-ops-control`; Nginx can neither read panel recovery secrets nor the privileged socket.
- Site database secrets are site-UID-only; transient plaintext database dumps use the control group for the panel backup worker but remain unreadable to `www-data`.
- Typed cron jobs installed as site-user cron entries with a five-minute timeout and non-overlapping `flock` execution.
- Node/Next deployments and rollbacks restart their constrained systemd runtime after the release switch.
- Git clones and Dockerized builds run under the site UID with a sanitized environment; Docker containers are pinned to the site UID/GID and receive no host socket or control-plane credentials.
- Site deletion removes typed database schemas/users/ACLs before removing the site workspace; failures stop the destructive job.

The development workstation is intentionally not treated as a production host. Live acceptance
requires a clean Ubuntu Server 24.04 LTS amd64 node with the services listed by `npm run acceptance`.
The panel process itself is capped at 256 MiB by the supplied systemd unit; a 1 vCPU / 1 GiB node is
the micro-profile floor for a small site, not a promise that a mixed multi-site workload or local
Node builds will fit inside 1 GiB.

## Run

Node 26 is required because the control plane uses `node:sqlite`.

```bash
npm install
npm run build
npm run server
```

Open `https://127.0.0.1:8787` (or `https://server-ip:8787` on a remote host). The first start creates a persistent self-signed certificate under the panel data directory; accept the browser warning for that certificate, then create the owner account with username, email, and password in the setup screen. No email service is used. `PANEL_ADMIN_TOKEN` is optional for unattended/test installs; a configured live token remains supported for upgrades. If `PANEL_SECRET_KEY` is not supplied, the server creates a persistent `/var/lib/quiet-ops/.panel-secret` file. Without the backup key, the local development process uses a non-recoverable in-memory key and labels backups accordingly. The Settings page can enroll an authenticator (TOTP) and issue one-time recovery codes; after enrollment, send the current code in `x-panel-totp` or use one recovery code in `x-panel-recovery`.
Set `PANEL_TLS_HOST` to the public IP or hostname when binding to `0.0.0.0`; it is included as the certificate SAN on first generation. This certificate is intentionally self-signed for first-run access and will show a browser trust warning; replace it with a trusted certificate when a domain/ACME endpoint is available.

For the UI development server:

```bash
npm run dev
```

The host adapter is safe dry-run by default. `PANEL_LIVE=1` is accepted only when the panel receives a non-dry-run response from `panel-agentd`; the agent itself remains non-mutating unless `PANEL_AGENT_LIVE=1` is explicitly set in its protected environment. On a production node, set both only after the Ubuntu 24.04 acceptance suite has passed. OpenLiteSpeed/LSPHP still requires the operator to install and review the vendor package, vhost/listener mapping, and LSAPI external-app name before the full OLS gate can pass.

Live mode refuses to start with the development token or without a stable recovery key.

The HTTP listener binds to `127.0.0.1` by default. For an AI client on a private VPN, set `PANEL_BIND` to the private interface and configure `PANEL_ALLOWED_ORIGIN`; keep bearer-token authentication and MFA enabled. A reverse proxy or VPN boundary is required before allowing non-local MCP access. If you intentionally bind the panel to a public address, put it behind HTTPS and use the browser sign-in screen; the UI never falls back to the development token in a live deployment.

## Go host agent

```bash
cd agent
go build -o panel-agentd .
```

The agent accepts only allowlisted typed actions and rejects arbitrary commands and path escapes. Live converge writes per-site Nginx/OLS includes and Node/Next systemd units with a dedicated site identity; Docker containers are started only by the root agent, run as the site UID/GID, and never receive the Docker socket. Release publication swaps the `current` symlink with a rollback-safe staging path; deprovision removes the unit and edge includes. Nginx configuration is tested before reload. Database, Docker, ACME, and rollback acceptance require the corresponding Ubuntu services.

On the approved host, `sudo scripts/host-bootstrap.sh` installs the reviewed Ubuntu packages (Nginx, PHP 8.3-FPM, database engines, Redis, Docker, Git, SSH, and Certbot). OpenLiteSpeed/LSPHP and Node 26 are installed from their reviewed vendor sources; after installing them, run `sudo scripts/install.sh`.

## Test

```bash
npm test
npm run check
npm run acceptance
npm run acceptance -- --full
```

`acceptance` is a read-only host gate. The base mode requires Ubuntu 24.04 amd64 plus active Nginx/PHP-FPM/cron services, Docker, Git, Certbot, MariaDB/PostgreSQL/Redis clients, SSH, cron helpers, systemd, cgroup v2, and a control-group separation that keeps `www-data` away from the agent socket; `--full` additionally requires an active OpenLiteSpeed service.

## Design notes

The control plane is intentionally outside the live traffic path. Existing generated site state remains available if the panel is stopped. MCP is an adapter over the same operations as the UI and CLI; it does not receive a root shell or existing plaintext secrets. A human terminal and AI workspace are separate capabilities.
